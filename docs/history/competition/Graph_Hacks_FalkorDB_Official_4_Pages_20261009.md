# 1. Overview：赛事概览

**原始页面**：https://www.wemakedevs.org/hackathons/falkordb

## 1.1 比赛主旨（The challenge）

**主题名称：Give your agent the context to act**。

[官方明确] 赛事关注 AI Agent 在行动时能否充分理解“数据之间的关系”，而非只获得孤立片段。项目应构建一个实际工作的单 Agent 或多 Agent 系统，并使用 FalkorDB 作为**上下文层（context layer）**。图结构必须真正影响 Agent 的判断与行为，不能只是附属的可视化层。

官方描述的核心问题包括：

1. Agent 通常只看到零散信息，缺乏整体关联视角。
2. 跨会话时容易丢失过去发生的事情。
3. 无法理解人员、系统、项目、记录之间的复杂关系。
4. 不容易解释自己为什么作出特定决策。

官方希望通过图中的实体、关系与可追溯路径组织数据、记忆及业务知识，让 Agent 能够利用已有关系进行决策，而不是仅靠推测。

**产品目标可归纳为三项**：[归纳]
- **Connected data**：根据多个实体之间的关系理解任务并采取行动。
- **Persistent memory**：保存与复用经验或历史信息，不局限于当前会话。
- **Traceable reasoning**：展示答案、操作或决策背后的连接与依据。

### 官方列出的图应承担的五项工作

1. 穿越不同数据记录间的连接关系。
2. 在会话之间保留记忆。
3. 在多个 Agent 间共享状态。
4. 连接人员、项目及决策。
5. 呈现结论背后的关系路径。

### 挑战区的四项补充说明

- **One agent problem**：找出一个确实需要理解关联关系的任务，并用 Agent 解决。
- **Solo or a team of four**：可单人或最多四人组队参与。
- **Open worldwide**：全球在线、免费参加、无需图数据库使用经验。
- **Three tracks**：赛道围绕关联数据驱动的行动、记忆与协调、企业知识大脑展开。

## 1.2 赛道 01：Agents That Act on Connected Data

**中文理解：基于关联数据采取行动的智能体。**

**项目目标**：[官方明确] Agent 应当依据图数据库查询到的关联事实作出决策，并执行有意义的任务。

**官网给出的场景举例**：
- 识别或调查欺诈行为。
- 对安全风险发现进行分流、研判和处理。
- 基于代码仓库的结构与依赖关系完成工程任务。

**五个关键关注点**：
1. Multi-hop reasoning：多跳关联推理。
2. Graph queries and algorithms as agent tools：把图查询与算法纳入 Agent 工具集。
3. Tool selection through MCP：通过 MCP 进行工具选择。
4. Actions based on what the graph shows：执行动作要有图结构证据支撑。
5. Explainable results：结果具有可解释性。

## 1.3 赛道 02：Agent Memory and Coordination

**中文理解：智能体记忆与多智能体协作。**

**项目目标**：[官方明确] 创建跨会话长期保存记忆、能够共享状态的 Agent 系统。记忆不应只是存放，还要随时间更新，并能供需要它的 Agent 使用。

**五个关键关注点**：
1. Episodic, semantic, and procedural memory：情景、语义及程序性记忆。
2. Persistent conversation history：持久化对话历史。
3. Shared state and handoffs between agents：Agent 间共享状态与工作交接。
4. High-concurrency reads and writes：高并发读写。
5. Separate memory per user or tenant：用户 / 租户间的记忆隔离。

## 1.4 赛道 03：Company Brain

**中文理解：企业知识大脑。**

**项目目标**：[官方明确] 让 Agent 理解公司的人员、团队、项目、文件、决策等组成元素，通过统一的关系图回答跨业务问题，并进一步执行任务。

**五个关键关注点**：
1. 将文档、工单与聊天中的知识汇入同一图结构。
2. 找出职责归属与领域知识拥有者。
3. 将决策追溯到原始来源。
4. 组织知识更新以跟随实际业务变化。
5. 回答应具有清晰可核对的来源。

## 1.7 Why graphs：为什么需要图

**主题：Agent 面临的问题本质上往往关于关系。**

官网用四类问题解释图数据库的作用（以下是中文意译）：

1. 与某笔已被标记的可疑交易存在关联的是哪些账户？
2. 某位客户上个月提出了什么要求，事情是否得到解决？
3. 哪些团队成员曾经参与过某个系统的工作？
4. 如果某项服务宕机，会有哪些其他系统受到影响？

[官方观点] 很多复杂问题的答案跨越多个记录，图数据库直接保存关系，便于 Agent 做路径追踪，而不必在每一步都重新拼接零散记录。

## 1.8 FalkorDB：技术定位与展示能力

**页面定位**：面向 AI Agent 的开源图数据库，适合作为持续读写的上下文系统。

### 官方在 Overview 中强调的能力

- 高速图遍历，可被 Agent 工作循环频繁调用。
- 单个实例承载多张隔离图；页面以用户、Agent、租户为隔离对象举例。
- 支持本机 Docker 使用。
- 图可以持续读写，跨会话再次使用。
- 场景包括 Agent 记忆、多 Agent 共享状态、企业关联知识。
- Browser 可对数据模型、关系及 Cypher 查询进行可视化检查。

### 页面展示的安装入口

```bash
docker pull falkordb/falkordb:latest
```

> 注意：这里是 Overview 展示的**拉取镜像命令**，并不是启动数据库服务的完整命令。启动方式参见资源页的 Docker 教程。

### 官网列出的官方客户端语言（7 种）

`Python`、`Node.js`、`Java`、`Rust`、`Go`、`PHP`、`C#`。

### 官网列出的 Agent / 图检索生态集成（7 项）

`GraphRAG-SDK`、`QueryWeaver`、`MCP`、`Graphiti`、`Cognee`、`LangChain`、`LlamaIndex`。

> 上述共 **7 项**，按网页可见名称逐一列出。该列表表示网页展示的生态入口，不意味着自动集成或每种能力均原生提供。

### 多租户 / 多图能力

官方提出可在一个实例中创建多张逻辑隔离图，避免为每个用户或租户分别部署数据库实例。这是产品能力描述，不是本次赛题规定“必须实现多租户”。

### Cypher 示例展示的实际逻辑

网站展示了一个以 `Person`—`Project`—`System` 关联为基础的查询示例：给出某系统名称，通过 `WORKED_ON`、`USES` 等关系，找出曾参与相关项目的人员，并按项目数量排序，最多返回 5 人。

该示例意在表明：一个较短的图查询可以跨实体回答“谁熟悉这个系统”，并支持 Agent 获取事实依据。完整示例代码请直接看 Overview 原页。

### 页面提及的图算法与能力

- Shortest path：最短路径。
- PageRank：节点重要性 / 排名。
- Centrality：中心性。
- Connected components：连通分量。
- Community detection：社区发现。

### 规则 01｜人数与唯一团队归属

可单人参赛；团队最多 4 名成员。每名参赛者只能属于一个参赛团队。

### 规则 02｜必须使用 FalkorDB

FalkorDB 必须是项目的**主要图数据库**，并支撑产品中的中心性、关键性能力。仅在项目中包含其依赖或名称不等于满足要求。

### 规则 03｜图必须产生真实功能贡献

如果图只是覆盖在传统数据存储上的一层图形可视化，就不符合要求。官方强调一个有力的反事实检验：**移除 FalkorDB 后，产品是否仍能正常完成原本的核心功能？** 如果仍然可以，就很可能表明图没有承担真实工作。

### 规则 04｜部署形式与技术栈自由

FalkorDB Docker、本地/自托管、FalkorDB Cloud 均可；搭配的编程语言、框架、前端和部署平台不限。

### 规则 05｜开放赛题与赛道声明

赛题在三个主题赛道内开放选题：
- Agents That Act on Connected Data
- Agent Memory and Coordination
- Company Brain

可报名任意一个乃至全部三个赛道；提交时必须列明自己参与的每个赛道。

### 规则 06｜数据合法性与限制

项目只能使用有权使用的数据，例如公开数据、合成数据或自己拥有的数据。官网明确禁止向图中装入私人、需要登录、付费墙、个人或其他受限信息。

> 不应将“自己有账号能够访问”自动理解为“比赛允许装载”。使用个人数据、第三方业务记录和私有代码尤其应谨慎。

### 规则 07｜正式比赛窗口

2026 年 10 月 15 日 00:01 IST 开始，10 月 18 日 23:59 IST 结束，提交入口在该时刻关闭。

### 规则 08｜主要设计与编码必须在开赛后进行

**Main coding and design work** 必须在开赛后才开始。赛前允许的活动包括讨论想法、写笔记、勾勒图数据模型、准备示意图。

> **这是 GraphSwarm 当前最需要关注的合规点之一。** 预研、通用工具准备与正式提交作品的原创实现应清楚区分。不能仅凭本文自行认定赛前已经完成的具体核心代码可直接作为赛期新作品提交。

### 规则 09｜允许使用的第三方基础

允许利用框架、开源库、公开 API、模板、第三方工具、公开数据集与素材。但评审对象是**比赛期间原创完成的工作**，不是复用材料本身。

### 规则 10｜每件提交作品的六项必备内容

官方要求每个项目都必须包含：

1. 公开的源代码仓库（public source-code repository）。
2. README：明确说明安装/运行步骤及**图数据模型**。
3. 产品依赖的 **Cypher 查询或图算法**。
4. 能够看到工作项目的**演示视频**。
5. **在线运行部署**；如确实无法部署，则给出**完整本地启动说明**。
6. 明确提交的赛道名称。

> 注意：这里的重点不只在于运行 Demo，还要求评审能够检查图模型与关键查询／算法。

### 规则 11｜允许 AI 辅助，但必须披露

允许使用 AI 编程助手；使用情况必须向主办方披露。不能因为 AI 帮忙开发就省略这项义务。

### 规则 12｜参赛者必须能解释技术实现

参赛者应理解并能解释：提交代码、图模型、查询逻辑、系统架构，以及支撑设计的技术决策。

### 规则 13｜完全依赖 AI 且缺乏实质贡献的作品可能遭拒

如果作品全部由 AI 生成，参赛者没有有意义的参与、验证或技术理解，官方可能拒绝该提交。**AI 工具的使用与作品是否合格是两个独立问题**。

### 规则 14｜主赛道奖品

官方重申总奖池价值 20,000 美元，三个主赛道分别为 iPhone 18 Pro、PS5 with GTA VI、M6 Mac Mini；获奖团队每名成员都能获得对应奖品。概览页还列有博客与 Top 50 附加奖。

### 规则 15｜知识产权归属

比赛期间产生的知识产权归创作者个人或创作者团队所有。主办方建议团队在提交前内部约定好成果所有权。

### 规则 16｜社区行为与尊重

必须尊重参赛者、组织者、赞助方、演讲者、评委及社区成员。

### 规则 17｜明确的取消资格情形

骚扰、歧视、剽窃或试图操纵评审程序，均会导致被取消资格。

### 规则 18｜违反规则与行为准则的后果

不遵守比赛规则或 WeMakeDevs 行为准则，可能被取消参赛资格。
